# AutoLuxe public demo deployment

The deployment target is one Render Free Node web service and a separate Neon Free PostgreSQL database. Express serves the built React app and `/api` on the same HTTPS origin. `render.yaml` prepares the service configuration; no provider account, database, repository publication, or deployment is created by these files.

## Before publishing

Use a fresh demo database and fictional demo data. Keep the audited original project separate from this deployment branch. Review the final changes and run the frontend build plus backend integration checks before making the service public. Never upload `backend/.env`, a database dump, or personal customer records. The migration path does not seed accounts or reset tables. On an empty fleet only, migration 002 adds eight fictional cars, including the three already featured on the homepage; an existing fleet is retained.

The existing `backend/seed.sql` is a legacy fixture and is not part of deployment. Do not run it against the hosted database. Database migrations run through `backend/scripts/migrate.js`, which records SHA-256 checksums and holds a transaction-scoped advisory lock. All unapplied migrations commit together, or all roll back. Already-applied migration files must remain unchanged; add a numbered migration for future schema updates. A failed migration stops startup.

## Provider setup and first deployment

1. After approving publication, publish only the reviewed deployment branch to a Git repository you control. Inspect the staged files for secrets first.
2. Create a Neon Free project in a region close to the Render service. Copy the connection string privately from Neon's connection dialog. Use the pooled endpoint for the web service and a least-privilege application role where practical. The hostname must remain unchanged for certificate verification.
3. In Render, create a Blueprint from that repository and this branch using `render.yaml`. Leave the root directory unset so the build can access both folders. Select the Free service plan and a nearby region. Supply `DATABASE_URL` through Render's secret environment-variable input. `JWT_SECRET` is generated by the Blueprint; keep it private.
4. Deploy. The build installs locked backend dependencies, installs frontend build dependencies, and produces `frontend/dist`. Startup applies the non-destructive migrations, then listens on Render's `PORT` at `0.0.0.0`. The public HTTPS address appears in the Render service dashboard after deployment succeeds.
5. Check `/api/health`, load the homepage, refresh a direct browser route such as `/cars`, and verify registration, login, fleet browsing, and role restrictions. Unknown `/api/...` endpoints must return JSON 404, never the React page. `/api/health` reports process liveness only; verify the database separately by browsing cars.
6. Create the first administrator using the private CLI described below. Verify the seeded fictional fleet and its featured-car links; add other fictional cars through the authenticated admin interface if needed. No admin account or password is embedded in the application.

Keep the Render and Neon credentials in their provider settings and a password manager. The application verifies the database's TLS certificate and hostname. It removes connection-string SSL flags before setting `rejectUnauthorized: true`; it never disables certificate checking. Node's normal certificate trust store supports Neon's public certificate authority. `channel_binding=require` in a provider URL should not be treated as application-enforced channel binding; verified TLS is the explicit guarantee here.

The production server requires a randomly generated `JWT_SECRET` of at least 32 characters and the built frontend. Do not copy a sample or placeholder secret. It bounds database connections and connection/query/statement timeouts. `TRUST_PROXY_HOPS=1` assumes the service is reachable through Render's proxy; adjust deliberately if the hosting topology changes. API requests remain on the page's origin, so global wildcard CORS is unnecessary. `VITE_API_URL` normally remains unset; an override must be a same-origin absolute path such as `/api`.

## Create the first administrator privately

Run this from a trusted local checkout with backend dependencies installed. Put the hosted `DATABASE_URL` into the ignored `backend/.env` privately and keep `NODE_ENV=development` for this local administrative CLI; it does not need the production JWT signing secret. TLS verification for `DATABASE_URL` remains enabled in every environment. Do not put the password in command arguments or shell history.

```powershell
node backend/scripts/bootstrap-admin.js --email "your-demo-admin@example.com" --first-name "Demo" --last-name "Administrator"
```

The CLI hides password entry and asks for confirmation on an interactive terminal. If a secure secret-management tool supplies stdin, it accepts exactly one password line. Use a unique password of at least 12 characters and no more than 72 UTF-8 bytes. It refuses when any administrator or the supplied email already exists; it does not promote existing users or reset passwords. There is no HTTP setup endpoint. Run migrations before using the CLI if the service has not started yet:

```powershell
node backend/scripts/migrate.js
```

## Local development with Docker

Copy `backend/.env.example` to `backend/.env` privately. Set a unique `PGPASSWORD` and random `JWT_SECRET`; for example, generate a secret in your own terminal with `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"`. Keep `DATABASE_URL` empty for the local Compose database.

```powershell
docker compose --env-file backend/.env up --build
```

Compose requires the private credentials, waits for PostgreSQL, and applies migrations before starting the backend. PostgreSQL is on an internal Docker network and has no published host port. The backend is bound only to the host's `127.0.0.1:5000`. The named `car_rental_data` volume persists between restarts; do not use `docker compose down -v` for routine updates. Changing the password environment variable does not rotate a password in an already-initialized PostgreSQL volume; perform any needed rotation deliberately inside the database.

Run the frontend separately in another terminal:

```powershell
npm ci --include=dev --prefix frontend
npm run dev --prefix frontend
```

Vite forwards `/api` to the backend. Use the URL printed by Vite. For an administrator in this local database, run the CLI inside the backend container so the private database stays unexposed:

```powershell
docker compose --env-file backend/.env exec backend node scripts/bootstrap-admin.js --email "demo-admin@example.test" --first-name "Demo" --last-name "Administrator"
```

The backend Dockerfile is for this local API container. The public deployment uses Render's native Node build to include the frontend output.

## Operations and limits

Customers can hold at most three pending bookings, each for 15 minutes. A rental lasts at most 30 days and must end within 365 days. These server-side bounds also appear in the booking UI. The server calculates prices from the locked fleet record in integer cents; customer-supplied prices cannot change the quote. Staff confirmation rechecks availability and rejects expired holds. Account deletion revokes an existing bearer token on its next request because authentication reloads the current user and role.

The login limiter permits 20 attempts per IP group and 10 per normalized account in 15 minutes; registration permits five attempts per IP group per hour. IPv6 addresses are grouped by /64. Counters expire, have bounded capacity, and remain process-local. Registration requires at least 12 characters and at most 72 UTF-8 bytes. Keep administrator credentials private and use fictional contact information for this demo.

Free hosting is appropriate for a project demonstration. Sleeping services and database compute can make the first visit slow; consult current provider quotas before presenting. Keep this as one web instance: the in-memory authentication limiter does not coordinate across multiple instances. The filesystem is not a durable upload store. Preserve the database when redeploying, take a private backup before schema changes, and retain a known working Git revision. Never run destructive schema resets as a deployment repair step.
